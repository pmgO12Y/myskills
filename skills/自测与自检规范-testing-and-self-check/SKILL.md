# 自测与自检规范

## 核心规则

### 1. 触发时机

**以下场景必须执行自测与自检：**

| 场景 | 触发条件 | 必做检查 |
|------|----------|----------|
| **代码编写完成** | 写完任何函数/模块/类后 | 单元测试 + 边界验证 |
| **代码修改完成** | 修改、重构、修复 Bug 后 | 回归测试 + 受影响范围验证 |
| **任务交付前** | 用户要求交付结果前 | 全量自检清单 |
| **用户明确要求** | 用户说"测试一下""检查一下" | 按用户指定范围检查 |

> **⚠️ 铁律**：代码不跑一遍就不算写完。光"看起来对"是不够的。

### 2. 自测流程（四步闭环）

每次写完代码后，按以下顺序执行：

```
1. 语法检查 → 2. 单元测试 → 3. 边界验证 → 4. 集成验证
```

#### 2.1 语法检查（必做，~10 秒）

- 用对应语言的 linter 检查一遍（ESLint、flake8、go vet、mypy 等）
- 确保没有未定义变量、类型错误、拼写错误
- **Must**：零语法错误才能进入下一步

#### 2.2 单元测试（必做）

**最小测试集必须包含：**

| 测试类型 | 说明 | 示例 |
|----------|------|------|
| **Happy Path** | 正常输入，验证核心逻辑正确 | `add(2, 3) === 5` |
| **边界条件** | 空值、零值、最大值、越界、空数组/字符串 | `add(0, 0) === 0`、`max([])` 应抛错 |
| **异常路径** | 错误输入、非法状态，验证是否优雅处理 | `add(null, 3)` 应抛 TypeError |
| **副作用检查** | 验证函数是否修改了不该改的外部状态 | 纯函数应无副作用 |

**覆盖率目标：**

| 代码类型 | 行覆盖率目标 | 分支覆盖率目标 |
|----------|-------------|---------------|
| 核心算法/业务逻辑 | **≥ 90%** | **≥ 85%** |
| 工具函数/辅助方法 | **≥ 70%** | **≥ 60%** |
| 简单 getter/setter | ≥ 50% | 可选 |

#### 2.3 边界验证（必做）

手动过一遍以下 checklist：

- [ ] 输入为空数组/空字符串/null/undefined 时会怎样？
- [ ] 输入为超大值（如 10^6 条数据）时会怎样？
- [ ] 输入包含特殊字符、 emoji、Unicode 时会怎样？
- [ ] 并发/异步场景有没有竞态条件？
- [ ] 循环是否会无限执行？
- [ ] 内存会不会泄漏？

#### 2.4 集成验证（涉及多模块时必做）

- 跑一遍完整调用链路，确认上下游接口对齐
- 数据库操作是否正常回滚？
- 文件 IO 是否正确关闭？
- 网络请求超时是否优雅降级？

## 质量门禁（Must / Should / Could）

### Must（不通过 = 不能交付）

| 检查项 | 标准 |
|--------|------|
| 语法错误 | 零语法错误 |
| 单元测试 | 全部通过，无失败 |
| 核心逻辑覆盖 | 行覆盖率 ≥ 90% |
| 边界处理 | 空值/越界/异常输入均已处理 |
| 安全风险 | 无 SQL 注入、XSS、命令注入等明显漏洞 |

### Should（强烈建议，可说明原因后豁免）

| 检查项 | 标准 |
|--------|------|
| 分支覆盖率 | ≥ 85% |
| 性能基准 | 在合理输入规模下响应时间可接受 |
| 代码风格 | 符合项目/语言的编码规范 |
| 文档注释 | 公共 API 有 JSDoc/Docstring |

### Could（加分项）

| 检查项 | 标准 |
|--------|------|
|  Mutation Testing | 变异测试通过率 ≥ 80% |
| 压力测试 | 在 10 倍负载下不崩溃 |
| 兼容性 | 跨浏览器/跨平台测试 |

## 代码测试规范

### 测试用例命名规范

| 语言 | 命名约定 | 示例 |
|------|----------|------|
| JavaScript/TypeScript | `describe` + `it('should ...')` | `it('should return sum of two numbers')` |
| Python | `test_` 前缀 + 下划线命名 | `test_calculate_sum_with_positive_integers` |
| Java | `@Test` + camelCase | `shouldReturnSumWhenGivenTwoPositiveIntegers` |
| Go | `Test` 前缀 + PascalCase | `TestCalculateSum` |

### 测试结构模板（AAA 模式）

```python
# Arrange（准备）
input_a = 2
input_b = 3
expected = 5

# Act（执行）
result = add(input_a, input_b)

# Assert（断言）
assert result == expected
```

### Mock 策略

| 场景 | 策略 | 注意 |
|------|------|------|
| 外部 API 调用 | 必须 Mock | 不要依赖真实网络请求 |
| 数据库查询 | 用内存数据库/事务回滚 | 不要污染真实数据 |
| 文件系统操作 | Mock fs 模块 | 或使用临时目录 |
| 时间/随机数 | Mock Date.now() / Math.random() | 确保测试可重复 |

> **⚠️ 警告**：不要过度 Mock。如果 Mock 了被测函数本身，测试就没意义了。

## 通用自检清单

### 代码交付前自检

- [ ] 代码能否编译/解释通过？
- [ ] 单元测试是否全部通过？
- [ ] 是否处理了所有边界条件？
- [ ] 是否有未使用的变量/导入/代码？
- [ ] 是否引入了循环依赖？
- [ ] 日志输出是否合适（无敏感信息、无调试残留）？
- [ ] 错误处理是否完善（不吞异常、给用户友好提示）？

### 文档交付前自检

- [ ] 文档结构是否完整（标题、目录、正文、附录）？
- [ ] 涉及流程的是否配了 Mermaid 图？
- [ ] 专业术语是否保留了英文原文并附中文解释？
- [ ] 修改记录是否已追加？
- [ ] 文件命名是否符合规范？

### 配置变更后自检

- [ ] 配置格式是否正确（JSON/YAML/TOML 无语法错误）？
- [ ] 必填项是否都有值？
- [ ] 敏感信息（密钥、密码）是否已脱敏？
- [ ] 变更是否向后兼容？

## 执行检查

每次交付前，逐项自检：

1. 是否执行了语法检查？
2. 单元测试是否全部通过？
3. 是否覆盖了 Happy Path、边界条件、异常路径？
4. 核心逻辑行覆盖率是否 ≥ 90%？
5. 是否手动验证了边界条件（空值、超大值、特殊字符）？
6. 修改代码后是否跑了回归测试？
7. 是否检查了安全风险（注入、XSS、越权）？
8. 错误处理是否完善？
9. 是否有未使用的代码或调试残留？
10. 交付物是否符合用户的原始需求？

## 踩坑经验

- 测试用例只测 Happy Path = 没测：必须包含边界和异常
- 覆盖率 100% 不代表没 Bug：覆盖率是必要条件，不是充分条件
- 不要在测试中写逻辑：测试代码应该直白、线性、易读
- 测试之间不要共享状态：每个测试应该独立可运行
- 异步测试必须 await：忘记 await 会导致测试假通过
- Mock 了被测函数 = 自欺欺人：Mock 的是依赖，不是被测对象本身
