# 专业测试规范

> 系统性的测试工程方法论。不是"怎么跑测试"，而是"怎么设计测试"。

---

## 一、核心原则

### 1.1 测试的本质

测试不是证明代码没有 Bug，而是**在有限资源内最大化发现缺陷的概率**。

| 误区 | 正确认知 |
|------|---------|
| 测试 = 验证功能正常 | 测试 = 探索系统行为边界 |
| 覆盖率 100% = 无 Bug | 覆盖率只是必要条件，非充分条件 |
| 测试是 QA 的事 | 测试是全员工程活动（Dev + QA + PM） |
| 上线前集中测试 | 测试左移，越早发现成本越低 |

### 1.2 测试设计第一性原理

1. **穷尽不可能** → 用科学方法选择最有价值的测试点
2. **缺陷集群性** → 80% 的 Bug 集中在 20% 的模块
3. **杀虫剂悖论** → 同一套用例反复执行，发现新缺陷的能力递减
4. **测试依赖于上下文** → 安全关键系统 vs 内部工具，策略完全不同

## 二、测试设计方法

### 2.1 黑盒设计方法

#### 等价类划分（Equivalence Partitioning）

将输入域划分为若干等价类，每类选一个代表测试。

```
输入条件：年龄 18-60 岁可注册

有效等价类：
- EC1: 18 ≤ 年龄 ≤ 60

无效等价类：
- EC2: 年龄 < 18
- EC3: 年龄 > 60
- EC4: 非数字输入
- EC5: 空值

测试用例：17, 18, 30, 60, 61, "abc", null
```

**规则**：
- 有效等价类：覆盖尽可能多的有效条件
- 无效等价类：每次只覆盖一个无效条件（避免屏蔽）
- 边界值必须单独测试（见 2.1.2）

#### 边界值分析（Boundary Value Analysis）

Bug 往往出现在边界。测试边界及边界两侧的值。

```
范围 [min, max] 的边界测试点：
- min - 1（略低于下界）
- min（下界）
- min + 1（略高于下界）
- max - 1（略低于上界）
- max（上界）
- max + 1（略高于上界）

示例：密码长度 6-20 位
测试点：5, 6, 7, 19, 20, 21
```

**扩展：健壮性边界值**
增加超出范围的极值测试（如 0, 空串, 超长串）。

#### 决策表（Decision Table）

适用于多条件组合场景。

```
规则：信用卡审批
条件：
- C1: 信用评分 ≥ 700
- C2: 收入 ≥ 月薪 3 倍
- C3: 无逾期记录

动作：
- A1: 通过
- A2: 人工审核
- A3: 拒绝

| 规则 | R1 | R2 | R3 | R4 | R5 | R6 | R7 | R8 |
|------|----|----|----|----|----|----|----|----|
| C1   | T  | T  | T  | T  | F  | F  | F  | F  |
| C2   | T  | T  | F  | F  | T  | T  | F  | F  |
| C3   | T  | F  | T  | F  | T  | F  | T  | F  |
| A1   | X  |    |    |    |    |    |    |    |
| A2   |    | X  | X  |    | X  |    |    |    |
| A3   |    |    |    | X  |    | X  | X  | X  |

简化：合并同类规则（如 R6-R8 可合并为 C1=F, C3=F）
```

#### 状态迁移测试（State Transition）

适用于有明确状态机的系统。

```
状态：未登录 → 已登录 → 订单页 → 支付中 → 支付成功

测试覆盖：
1. 正常路径：未登录 → 登录 → 下单 → 支付 → 成功
2. 异常路径：支付中 → 取消 → 订单页
3. 非法跳转：未登录 → 直接访问支付页（应重定向）
4. 状态持久化：刷新页面后状态保持
```

#### 场景法（Scenario Testing）

基于用户真实使用场景设计端到端测试。

```
场景：电商下单
- 主场景：浏览 → 加购 → 结算 → 支付 → 确认
- 备选：浏览 → 加购 → 修改数量 → 结算 → 支付
- 异常：支付失败 → 重试 → 成功
- 边界：库存刚好为 1 时下单
```

### 2.2 白盒设计方法

#### 语句覆盖（Statement Coverage）

每行代码至少执行一次。最弱标准。

#### 判定覆盖 / 分支覆盖（Branch Coverage）

每个判断的 True/False 分支都执行。

```python
def can_vote(age, citizen):
    if age >= 18 and citizen:  # 需覆盖: TT, TF, FT
        return True
    return False

# 分支覆盖用例：
# (20, True) → TT
# (20, False) → TF
# (16, True) → FT
```

#### 条件覆盖（Condition Coverage）

每个条件的 True/False 都出现。

```python
# age >= 18 and citizen
# 需覆盖: age>=18=T/F, citizen=T/F
# (20, True), (16, False) 满足条件覆盖
# 但可能不满足分支覆盖（缺少 TF 或 FT）
```

#### 路径覆盖（Path Coverage）

所有可能的执行路径。最强但通常不可行（指数级增长）。

**实践建议**：
- 核心逻辑追求分支覆盖 ≥ 80%
- 安全关键代码追求 MC/DC（Modified Condition/Decision Coverage）
- 工具函数追求条件覆盖

### 2.3 基于经验的测试

#### 错误推测法（Error Guessing）

基于经验推测易错点：
- 除零、空指针、数组越界
- 并发竞态、资源泄漏
- 时区/闰年/夏令时
- 特殊字符注入（SQL/XSS）

#### 探索式测试（Exploratory Testing）

同时设计测试和执行测试，依赖测试人员的领域知识。

**适用场景**：
- 新功能快速验证
- 复杂业务逻辑理解
- 用户验收前最后一轮

## 三、测试分层策略

### 3.1 测试金字塔

```
        /\
       /  \      E2E 测试（少而精）
      /____\
     /      \    集成测试（适中）
    /________\
   /          \  单元测试（大量）
  /____________\
```

**比例建议**：
- 单元测试：70%
- 集成测试：20%
- E2E 测试：10%

**反模式：冰淇淋锥**

```
        /\
       /  \      大量手工测试
      /____\
     /      \    大量 E2E
    /________\
   /          \  少量单元测试
  /____________\
```

### 3.2 各层职责

| 层级 | 范围 | 速度 | 稳定性 | 定位问题 |
|------|------|------|--------|---------|
| **单元测试** | 单个函数/类 | < 10ms | 高 | 精确到行 |
| **集成测试** | 模块间交互 | < 1s | 中 | 精确到接口 |
| **契约测试** | 服务间 API 契约 | < 1s | 高 | API 兼容性 |
| **E2E 测试** | 完整用户流程 | > 5s | 低 | 业务流程 |

### 3.3 分层选择决策树

```
要测试什么？
├── 单个函数的逻辑正确性 → 单元测试
├── 两个模块的数据流转 → 集成测试
├── 微服务间的 API 契约 → 契约测试（Pact）
├── 用户完整操作流程 → E2E 测试
└── 系统整体性能表现 → 性能测试
```

### 3.4 测试左移与右移

**左移（Shift Left）**：
- 需求评审时识别可测试性风险
- 代码评审时关注测试覆盖
- 开发阶段编写单元测试（TDD/BDD）

**右移（Shift Right）**：
- 生产环境监控 = 持续测试
- A/B 测试验证业务假设
- 混沌工程验证系统韧性

## 四、测试架构

### 4.1 测试数据管理

#### 数据工厂模式（Test Data Factory）

```python
# 不要这样
user = User(name="test", email="test@test.com", age=25, ...)

# 要这样
user = UserFactory.create(age=25)  # 其余字段使用合理默认值
admin = UserFactory.create_admin()
user_with_orders = UserFactory.create_with_orders(order_count=3)
```

#### 数据隔离策略

| 策略 | 实现 | 适用场景 |
|------|------|---------|
| 内存数据库 | SQLite/H2 | 单元测试 |
| 事务回滚 | @Transactional | 集成测试 |
| 独立 Schema | 每次测试新建 Schema | 并行执行 |
| 数据清理 | @AfterEach 清理 | 遗留系统 |

### 4.2 Mock vs Stub vs Fake vs Spy

| 类型 | 定义 | 适用场景 |
|------|------|---------|
| **Dummy** | 仅填充参数，不会被使用 | 方法签名需要但逻辑不依赖 |
| **Stub** | 预设返回值 | 隔离外部依赖，控制输入 |
| **Spy** | 记录调用信息 | 验证方法被调用（次数/参数） |
| **Mock** | 预设期望行为 + 验证 | 验证交互行为 |
| **Fake** | 简化实现（如内存 DB） | 需要真实行为但不想用真实依赖 |

**选择原则**：
- 需要验证行为 → Mock
- 只需要控制输入 → Stub
- 需要近似真实行为 → Fake
- 不要过度 Mock（见「自测与自检规范」常见测试陷阱）

### 4.3 测试可维护性

#### Page Object 模式（UI 测试）

```python
# 不要这样
browser.click("#login-button")
browser.fill("#username", "admin")

# 要这样
login_page = LoginPage(browser)
login_page.login_as("admin", "password")
# 选择器变化只需改一处
```

#### 测试代码质量要求

测试代码是生产代码，同样要求：
- DRY：提取公共 setup/teardown
- 可读性：测试名即文档 `should_return_error_when_user_not_found`
- 独立性：测试之间不共享状态
- 快速反馈：单测 < 100ms，全量 < 5min

## 五、专项测试

### 5.1 性能测试

#### 类型矩阵

| 类型 | 目的 | 负载 | 持续时间 |
|------|------|------|---------|
| **基准测试** | 建立性能基线 | 单用户 | 短 |
| **负载测试** | 验证预期负载下表现 | 预期峰值 | 中等 |
| **压力测试** | 找到系统极限 | 超过峰值 | 直到崩溃 |
| **稳定性测试** | 验证长期运行稳定性 | 正常负载 | 数小时/天 |
| **峰值测试** | 验证突发流量应对 | 突发峰值 | 短 |

#### 关键指标

- **吞吐量（Throughput）**：每秒处理请求数（TPS/QPS）
- **响应时间（Latency）**：P50/P95/P99，关注长尾
- **错误率**：> 0.1% 通常不可接受
- **资源利用率**：CPU/Memory/IO/Network

#### 工具选择

| 场景 | 工具 |
|------|------|
| HTTP API | k6, JMeter, Gatling |
| 数据库 | sysbench, pgbench |
| 前端 | Lighthouse, WebPageTest |
| 全链路 | APM（SkyWalking, Jaeger） |

### 5.2 安全测试

#### OWASP Top 10 快速检查

| 风险 | 测试要点 |
|------|---------|
| 注入（Injection） | SQL/NoSQL/OS/LDAP 注入测试 |
| 失效访问控制 | 水平/垂直越权测试 |
| 敏感数据泄露 | 传输加密、存储加密、日志脱敏 |
| XSS | 反射型/存储型/DOM 型输入验证 |
| 安全配置错误 | 默认密码、目录遍历、信息泄露 |

#### 安全测试方法

1. **静态分析（SAST）**：SonarQube, CodeQL, Semgrep
2. **动态分析（DAST）**：OWASP ZAP, Burp Suite
3. **依赖扫描**：Snyk, OWASP Dependency-Check
4. **渗透测试**：专业安全团队执行

### 5.3 兼容性测试

| 维度 | 覆盖策略 |
|------|---------|
| 浏览器 | Chrome/Firefox/Safari/Edge 最新 2 版 + IE11（如需） |
| 移动端 | iOS Safari + Android Chrome，主流分辨率 |
| 操作系统 | 目标用户主要使用的 OS 版本 |
| 数据库 | 开发/测试/生产使用同一版本 |
| API 版本 | 向后兼容至少 1 个主版本 |

## 六、测试文档规范

### 6.1 测试计划模板

```markdown
# 测试计划

## 1. 范围
- 测试目标
- 测试范围（In/Out of Scope）

## 2. 策略
- 测试层级与比例
- 自动化 vs 手工比例
- 环境要求

## 3. 资源
- 人员与分工
- 时间计划
- 工具与环境

## 4. 风险
- 风险识别与应对

## 5. 准入/准出标准
- 准入：开发完成、单元测试通过、代码评审通过
- 准出：P0 用例 100% 通过、无 P0/P1 缺陷开放、性能达标
```

### 6.2 测试用例模板

| 字段 | 说明 |
|------|------|
| ID | 唯一标识（如 TC-LOGIN-001） |
| 模块 | 所属功能模块 |
| 优先级 | P0（阻塞）/ P1（重要）/ P2（一般）/ P3（边缘） |
| 前置条件 | 执行前必须满足的条件 |
| 测试步骤 | 编号、清晰、可重复 |
| 输入数据 | 具体值或引用数据工厂 |
| 预期结果 | 明确、可验证 |
| 实际结果 | 执行时填写 |
| 状态 | 通过/失败/阻塞/跳过 |

### 6.3 缺陷报告规范

**好的缺陷报告**：
```markdown
标题：[登录] 输入特殊字符导致 500 错误

环境：Staging, Chrome 120, macOS 14

重现步骤：
1. 访问 /login
2. 用户名输入 "admin' OR '1'='1"
3. 点击登录

预期结果：提示用户名格式错误
实际结果：返回 500 Internal Server Error

附件：截图、日志、curl 命令
```

## 七、质量度量

### 7.1 代码覆盖率

| 类型 | 说明 | 目标 |
|------|------|------|
| 语句覆盖 | 执行过的语句比例 | ≥ 70% |
| 分支覆盖 | 执行过的分支比例 | ≥ 60% |
| 函数覆盖 | 调用过的函数比例 | ≥ 80% |
| 行覆盖 | 执行过的代码行比例 | ≥ 70% |

**覆盖率陷阱**：
- 高覆盖率 ≠ 高质量测试
- 只测 Happy Path 也能有 80% 覆盖率
- 应结合变异测试（Mutation Testing）验证测试有效性

### 7.2 缺陷度量

| 指标 | 计算方式 | 意义 |
|------|---------|------|
| 缺陷密度 | 缺陷数 / 代码行数（千行） | 代码质量趋势 |
| 缺陷移除效率 | 测试发现数 / 总缺陷数 | 测试有效性 |
| 缺陷逃逸率 | 生产发现数 / 总缺陷数 | 测试漏检率 |
| MTTR | 平均修复时间 | 响应速度 |

### 7.3 测试有效性度量

- **变异测试得分**：人工注入缺陷，测试能发现的比例
- ** flaky 测试比例**：不稳定测试占比应 < 5%
- **测试维护成本**：新增功能时测试修改量

## 八、执行检查（AI 自检清单）

当用户请求涉及测试设计、测试方案、测试评审时，逐项确认：

### Must（必须）
- [ ] 明确了测试目标和范围
- [ ] 选择了合适的测试设计方法（等价类/边界值/决策表/场景法）
- [ ] 覆盖了 Happy Path + 边界条件 + 异常路径
- [ ] 测试用例有明确的预期结果
- [ ] 用例有优先级分级（P0/P1/P2）

### Should（应该）
- [ ] 考虑了测试数据策略（工厂模式/隔离策略）
- [ ] 明确了自动化 vs 手工的分配
- [ ] 包含了准入/准出标准
- [ ] 识别了主要风险并制定了应对

### Could（可以）
- [ ] 提供了性能/安全/兼容性测试建议
- [ ] 包含了测试环境要求
- [ ] 给出了工具推荐

## 十、踩坑经验

（以下由 AI 在实际调用中自动积累）

- 测试用例设计 / 等价类划分：无效等价类每次只覆盖一个，避免多个无效条件互相屏蔽
- 性能测试 / 基准建立：必须先建立基线再比较，没有基线的性能数据无意义
- 安全测试 / SQL 注入：不要只测单引号，双引号、反斜杠、Unicode 编码都要覆盖
- E2E 测试 / 选择器维护：避免使用动态生成的 CSS 选择器，优先使用 data-testid 属性
- 契约测试 / 消费者驱动：先写消费者期望，再验证提供者实现，顺序不能反
