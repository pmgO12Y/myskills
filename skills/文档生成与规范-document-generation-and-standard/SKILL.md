# 文档生成与规范

## 核心规则

### 1. 可读性优先

- **任何文档段落长度不得超过 5 行**
- 复杂逻辑必须拆分为**列表**或**表格**，**优先使用表格**
- 禁止大段纯文字堆砌

### 2. 图文并茂（强制）

凡是涉及以下内容的描述，**严禁只用纯文字**：
- 业务流程
- 数据流转
- 页面跳转
- 状态变化

**必须配套：**
- **Mermaid** 代码块绘制流程图、时序图或状态图
- 若无法使用 Mermaid，必须提供 **ASCII 结构框图**

### 3. 排版与醒目规范

文档排版必须清晰、醒目、易读，优先使用以下方式呈现信息：

#### 3.1 优先使用表格

- 复杂逻辑必须拆分为列表或表格，**优先使用表格**
- 当信息具有**对比性、多维度、可结构化**时，**优先使用表格**呈现
- 表格能提升信息密度和可读性，适合：参数对比、优缺点分析、步骤说明、数据展示
- **不要过度使用表格**：简单的一句话说明、纯文本叙述不需要表格

**列表 vs 表格选择指南：**

| 场景 | 推荐方式 |
|------|----------|
| 简单罗列（3-5 项，无多维度） | 列表 |
| 多维度对比、参数说明、状态对照 | **表格（优先）** |
| 步骤说明（有明确顺序） | 编号列表 |
| 优缺点分析、方案对比 | **表格（优先）** |

**正确示例：**

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| A | 简单快速 | 扩展性差 | 小型项目 |
| B | 可扩展 | 学习成本高 | 大型项目 |

#### 3.2 关键字加粗

- **关键名词**、**核心结论**、**重要数值**、**警告信息**必须使用**加粗**强调
- 重要结论使用**引用块** `>` 突出
- 粗体占比不要超过全文的 20%，避免全部加粗等于没加粗

**正确示例：**
> **⚠️ 核心风险：** 此操作会**永久删除**数据，且**不可恢复**！

#### 3.3 适度使用 Emoji

- 可在文档中**适度**使用 emoji，增加可读性和视觉引导
- 推荐场景：状态标记、分类标识、重点提示
- 不要在专业术语解释中插入 emoji
- 避免连续使用过多 emoji（最多 2-3 个）

**常用 Emoji 对照表：**

| Emoji | 含义 | 使用场景 |
|-------|------|----------|
| ✅ | 正确/推荐 | 正确做法、推荐方案 |
| ❌ | 错误/禁止 | 错误做法、禁止行为 |
| ⚠️ | 警告/注意 | 风险提示、注意事项 |
| 🎯 | 目标/重点 | 核心目标、重点内容 |
| 📌 | 固定/备忘 | 重要备忘、关键信息 |
| 💡 | 提示/建议 | 优化建议、最佳实践 |
| 🔥 | 紧急/重要 | 紧急事项、高优先级 |
| 📊 | 数据/图表 | 数据展示、图表说明 |
| 📝 | 文档/记录 | 文档要求、变更记录 |
| 🚀 | 发布/上线 | 版本发布、功能上线 |

**正确示例：**
- **✅ 推荐方案：** 使用 **immutable**（**不可变**）数据结构
- **❌ 错误做法：** 直接修改原数组
- **⚠️ 注意：** 此操作不可逆

#### 3.4 代码块与行内代码

- 技术术语、文件名、短代码使用行内代码：`config.json`、`function()`
- 配置示例、命令行使用代码块：
  ```bash
  npm install
  ```

#### 3.5 分隔线与标题层级

- 使用 `---` 分隔不同板块
- 使用标题层级（`#`、`##`、`###`）组织文档结构
- 同一文档内保持层级一致

## 文档版本策略总则

所有文档遵循**不丢失历史**原则，但归档/记录方式因生命周期不同而灵活处理。

### 版本策略四分法

| 策略 | 适用文档 | 版本管理 | 旧文档处理 | 修改记录方式 |
|------|----------|----------|------------|-------------|
| **迭代型** | BRD、MRD、PRD、用户手册、API文档、测试计划、测试用例、测试报告 | 语义化版本 (Vx.y.z) | 新版另存，旧版保留 | 文档内修改记录表 |
| **事件型** | ADR、RFC | 递增编号 (ADR-001) | 批准后冻结，supersede 机制 | 文档内修改记录表 |
| **活文档型** | Runbook、数据字典 | 覆盖更新 | 旧版归档到 `归档/` 子目录 | 文档内修改记录表 |
| **单次型** | 事故复盘、缺陷报告 | 不版本化 | 天然不覆盖（每份独立） | 外置统一修改日志 |

### 归档机制（活文档型适用）

覆盖更新前，必须将当前版本复制到 `归档/` 子目录：

- **归档目录**：放在需要归档的父目录下（如 `部署运维/归档/`、`数据库设计/归档/`）
- **归档命名**：`[文档类型]_[主题]_V[版本号]_[YYYYMMDD].md`
- **示例**：`归档/Runbook_发布流程_V1.0.0_20260420.md`

### 外置修改日志（单次型适用）

事故复盘和缺陷报告的修改记录不放在文档内，而是统一记到外部日志文件：

- **事故复盘** → `docs/技术文档/部署运维/复盘修改日志.md`
- **缺陷报告** → `docs/测试文档/缺陷修改日志.md`

**修改日志格式：**

| 序号 | 文档名 | 修改时间 | 修改内容 | 修改人 |
|------|--------|----------|----------|--------|
| 1 | Postmortem_20260420_支付故障.md | 2026-04-21 10:00 | 补充根因分析 | 张三 |
| 2 | Bug_20260424_支付超时.md | 2026-04-25 14:30 | 更新修复状态 | 李四 |

## 文档修改流程

### 迭代型文档（BRD/MRD/PRD/用户手册/API文档/测试计划/用例/报告）

当用户要求修改已有文档时，必须遵循以下流程：

1. **读取旧版文档**：先读取最新版本的文档内容
2. **基于旧版修改**：在旧版内容基础上进行修改，保留原有结构
3. **新建文件**：按版本规则升级版本号，新建文件（严禁覆盖旧版）
4. **更新修改记录**：在文档开头的修改记录表格中**追加新行**，包含：
   - **序号**：递增编号
   - **版本**：新版本的语义化版本号
   - **日期**：精确到秒（YYYY-MM-DD HH:MM:SS）
   - **修改内容**：具体修改了什么
   - **原因**：为什么修改
   - **影响范围**：影响哪些章节或模块
   - **状态**：当前修改记录的状态

### 事件型文档（ADR/RFC）

1. **读取旧版文档**：先读取当前文档内容
2. **检查状态**：若已「✅ 已批准」，则**不可修改**，需创建新文档 supersede
3. **若未批准**：可直接在文档内修改，更新修改记录
4. **Supersede 机制**：创建新 ADR/RFC，在旧文档「Superseded By」字段标注新编号

### 活文档型（Runbook/数据字典）

1. **读取当前文档**：先读取当前版本内容
2. **归档旧版**：将当前版本复制到 `归档/` 子目录，命名含版本号+日期
3. **覆盖更新**：在原文件上直接修改
4. **更新修改记录**：在文档修改记录中追加新行

### 单次型（事故复盘/缺陷报告）

1. **修改文档内容**：直接在文档内修改
2. **更新状态字段**：修改文档内的状态标记
3. **记录修改日志**：将修改细节追加到对应的外置修改日志文件

## 执行检查

每次生成文档前，自我检查：
1. 段落是否超过 5 行？
2. 复杂逻辑是否已拆分为列表或表格？
3. 涉及流程/流转/跳转/状态变化的内容是否配了 Mermaid 图？
4. 关键信息是否使用了加粗或代码块强调？
5. 结构化信息是否优先使用了表格？
6. Emoji 使用是否适度？
